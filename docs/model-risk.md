# เอกสารประกอบการพิจารณาความเสี่ยงโมเดล/AI (Model Risk Dossier)

เอกสารนี้ใช้ประกอบการขออนุมัติตามกระบวนการบริหารความเสี่ยงด้านโมเดล/AI ของธนาคาร ส่วนที่เป็นข้อเท็จจริงของระบบ
(เวอร์ชัน โมเดล คลังเอกสาร ผลการทดสอบ การตรวจมาตรการควบคุม) **สร้างอัตโนมัติจากระบบที่รันอยู่** ด้วย
`copilot evidence-pack` ไปที่ [`evidence/model-card.md`](evidence/model-card.md) ให้แนบไฟล์นั้นที่สร้างจากสภาพแวดล้อมที่ขออนุมัติจริง
ไม่ใช่ไฟล์ตัวอย่างใน repo (ซึ่งสร้างจากเครื่องพัฒนาและมีข้อค้นพบที่ต้องแก้ก่อน production)

> สถานะ: ต้นแบบที่ทดสอบแล้วในสภาพแวดล้อมพัฒนา **ยังไม่ผ่านการอนุมัติ** และยังมีเงื่อนไขที่ต้องปิดก่อนใช้จริง (หัวข้อ 9)

## 1. วัตถุประสงค์และขอบเขตการใช้

| | |
|---|---|
| ชื่อระบบ | Compliance Copilot — ผู้ช่วยค้นและอ้างอิงกฎระเบียบสำหรับธนาคารและธุรกิจหลักทรัพย์ |
| ใช้เพื่อ | ตอบคำถามของพนักงานจากกฎหมาย ประกาศหน่วยงานกำกับ และนโยบายภายใน พร้อมอ้างอิงถึงระดับมาตรา/ข้อ, เทียบนโยบายภายในกับกฎหมาย (Gap Analysis) เป็นรายการงานให้เจ้าหน้าที่ทบทวน |
| ผู้ใช้ | พนักงานทุกระดับ (สิทธิ์เห็นเอกสารตามชั้นความลับและแผนก), เจ้าหน้าที่ Compliance, ผู้ตรวจสอบภายใน, ผู้ดูแลระบบ |
| บทบาทของ AI | **ข้อมูลประกอบการตัดสินใจ** ไม่ใช่ความเห็นทางกฎหมายและไม่ตัดสินแทนคน ผู้ใช้ต้องยอมรับข้อตกลงนี้ก่อนใช้ (`config/terms.th.md`, บังคับฝั่งเซิร์ฟเวอร์เมื่อเปิด `COPILOT_TERMS_REQUIRED`) |
| **ห้ามใช้เพื่อ** | ตัดสินใจอัตโนมัติที่กระทบลูกค้า, ออกความเห็นทางกฎหมายต่อภายนอก, รายงานต่อหน่วยงานกำกับโดยไม่มีผู้มีอำนาจยืนยัน, เรื่องนอกคลังเอกสาร (ระบบถูกออกแบบให้ปฏิเสธ) |
| ผลกระทบหากผิด | พนักงานปฏิบัติผิดกฎ → ความเสี่ยงด้านกฎระเบียบและชื่อเสียง; ลดทอนด้วยการให้ตรวจต้นฉบับทุกครั้งและไม่ใช้ในการตัดสินใจอัตโนมัติ |

## 2. สถาปัตยกรรมโดยสรุป (รายละเอียด: [architecture.md](architecture.md))

คำถาม → ตรวจ prompt injection → ปิดบังข้อมูลส่วนบุคคล → ค้นหาแบบผสม (vector + BM25 + อ้างอิงตรง) โดยกรองสิทธิ์และวันที่มีผลใน SQL
และด้วย Row-Level Security → จัดอันดับใหม่ด้วย cross-encoder → **ถ้าหลักฐานอ่อนไม่เรียก LLM** → LLM สร้างคำตอบพร้อม quote →
**โค้ดตรวจว่า quote มีอยู่ในต้นฉบับจริง** → บันทึกใน audit log แบบ hash chain

หลักการที่ทำให้ประเมินความเสี่ยงได้ง่ายกว่า LLM ทั่วไป: (1) ความถูกต้องของการอ้างอิงตรวจโดยโค้ดที่กำหนดผลได้ ไม่ใช่โดยโมเดล
(2) สิทธิ์เข้าถึงบังคับที่ฐานข้อมูล ไม่พึ่ง prompt (3) การปฏิเสธเมื่อไม่มีหลักฐานเป็นพฤติกรรมหลัก

## 3. ข้อมูลและการไหลของข้อมูล

| ข้อมูล | ที่อยู่ | ส่งออกนอกองค์กรหรือไม่ |
|---|---|---|
| กฎหมาย/ประกาศสาธารณะ 8 ฉบับ | PostgreSQL (ตรึงด้วย SHA-256) | ไม่ |
| นโยบาย/คู่มือภายใน | PostgreSQL ตามชั้นความลับและแผนก | **ส่วนที่ผู้ใช้มีสิทธิ์และเกี่ยวข้องกับคำถาม ถูกส่งให้ผู้ให้บริการ LLM** |
| คำถามของผู้ใช้ | ประวัติแชต (ปิดบัง PII แล้ว, ลบได้, ลบอัตโนมัติตามอายุ) และ audit log | ส่งให้ LLM **หลังปิดบัง PII** (เลขบัตรประชาชน เบอร์โทร อีเมล เลขบัญชี บัตรเครดิต ชื่อบุคคล) |
| embedding / rerank | รันในเครื่อง | ไม่ |

ประเด็นที่ต้องตัดสินโดยธนาคาร: ผู้ให้บริการ LLM และภูมิภาค, สัญญา zero-retention/ไม่ใช้ข้อมูลฝึกโมเดล, และการส่งคู่มือชั้นลับให้ผู้ให้บริการภายนอก
(ทางเลือก: โมเดลในองค์กรผ่านอินเทอร์เฟซเดียวกัน) — ดู [security.md](security.md)

## 4. ทะเบียนความเสี่ยงและมาตรการควบคุม

| # | ความเสี่ยง | มาตรการ | หลักฐาน | ความเสี่ยงคงเหลือ |
|---|---|---|---|---|
| R1 | คำตอบผิด/แต่งขึ้น (hallucination) | ตรวจ quote กับต้นฉบับด้วยโค้ด, คำตอบที่ตรวจไม่ผ่านถูกแทนด้วยข้อความต้นฉบับ, ปฏิเสธเมื่อหลักฐานอ่อน | quote ตรงต้นฉบับ 95.9–98% ในชุดทดสอบ; คำตอบที่ยืนยันไม่ได้ 4 จาก 146 (ชุด extended) | **กลาง** — ตรวจได้ว่า quote มีจริง แต่ตรวจไม่ได้ว่าตีความถูก ต้องมีคนเทียบต้นฉบับ |
| R2 | ตอบจากกฎหมายฉบับเก่าหรือผิดฉบับ | ตอบตามฉบับที่มีผล ณ วันที่เลือก, ฉบับเก่าไม่ถูกลบ, เตือนเมื่อมีฉบับแก้ไขที่ยังไม่รวม, ตรวจต้นฉบับกับผู้เผยแพร่ (`check-updates`, CI รายสัปดาห์) | ชุดทดสอบเวอร์ชัน 10 ข้อ ผ่านทั้งหมด | **ต่ำ-กลาง** — ตรวจได้เฉพาะเอกสารที่อยู่ในรายการ กฎหมายฉบับใหม่ต้องมีคนเฝ้า |
| R3 | เปิดเผยเอกสารเกินสิทธิ์ | กรองสิทธิ์ใน SQL + Row-Level Security ชั้นที่สอง (fail closed), ตรวจสิทธิ์ซ้ำเมื่อเปิดประวัติแชต | รั่วไหล 0 ใน 218 คำถาม; เทสต์ที่ลบเงื่อนไขสิทธิ์ออกจาก SQL แล้วยังไม่รั่ว | **ต่ำ** |
| R4 | ข้อมูลส่วนบุคคลของลูกค้าหลุดไปยัง LLM/บันทึก | ปิดบัง PII ก่อนเรียก LLM, บันทึก/ประวัติเก็บเฉพาะข้อความที่ปิดบังแล้ว, ลบประวัติตามอายุ | ปิดบังครบ 6 จาก 6 กรณีที่มีข้อมูลส่วนบุคคลในชุดทดสอบ | **กลาง** — ตัวตรวจแบบกฎ ไม่รับประกันทุกรูปแบบ (เช่น ชื่อที่ไม่มีคำนำหน้า) |
| R5 | Prompt injection / พยายามเลี่ยงระบบ | ตัวกรองก่อนเรียกโมเดล, ข้อความในเอกสารถือเป็นข้อมูล, สิทธิ์ไม่ขึ้นกับโมเดล | บล็อก 9 จาก 9 กรณีโจมตี และไม่บล็อกคำถามกฎหมายที่ฟังคล้ายกัน (ตรวจทุกคำถามที่ต้องตอบ) | **ต่ำ-กลาง** — ตัวกรองแบบรูปแบบ มีวิธีโจมตีที่ไม่ได้ทดสอบ แต่สิทธิ์ไม่ถูกกระทบ |
| R6 | ผู้ใช้เชื่อคำตอบเกินควร | ข้อตกลงการใช้ที่ต้องยอมรับ, ป้ายสถานะคำตอบ, ป้ายสีแดงเมื่ออ้างอิงไม่ผ่าน, คู่มือและแผนอบรม ([user-guide.md](user-guide.md)) | ยอมรับข้อตกลงถูกบันทึกพร้อมเวอร์ชัน | **กลาง** — เป็นเรื่องพฤติกรรมคน วัดได้จากรายงานปัญหาและผลการอบรม |
| R7 | คุณภาพเสื่อมโดยไม่มีใครรู้ (เปลี่ยนโมเดล, เอกสารเสียหาย) | มาตรวัดความน่าเชื่อถือ (อัตรา quote ที่ตรวจผ่าน, อัตราคำตอบยืนยันไม่ได้, อัตราปฏิเสธ), กฎแจ้งเตือน 12 ข้อ, quality gate ใน CI ([deployment.md](deployment.md)) | กฎแจ้งเตือนตรวจด้วย promtool | **ต่ำ-กลาง** — ต้องมีคนรับแจ้งเตือนจริง |
| R8 | ผู้ให้บริการ LLM ล่ม/โควตาหมด | ถอยไปแสดงข้อความต้นฉบับ (ไม่ตอบมั่ว), เริ่มสร้างใหม่เมื่อ stream ถูกตัด | พบจริงระหว่างทดสอบ (503, โควตา) และระบบถอยตามออกแบบ | **ต่ำ** ด้านความถูกต้อง, **กลาง** ด้านความพร้อมใช้งาน |
| R9 | แก้บันทึกตรวจสอบย้อนหลัง | audit log แบบ hash chain, ตรวจซ้ำทุกชั่วโมงและแจ้งเตือนทันที | เทสต์การแก้ไข; แจ้งเตือน `AuditChainBroken` | **ต่ำ** — ผู้ดูแลฐานข้อมูลที่ลบทั้งท้ายโซ่ได้ ต้องสำรองข้อมูลแยก |
| R10 | บัญชีถูกเดารหัส/ใช้โควตา LLM เปลือง | ล็อกบัญชีหลังผิด 5 ครั้ง, rate limit ต่อผู้ใช้และที่อยู่, SSO | เทสต์ครอบคลุม; ทดสอบผ่านหน้าเว็บจริง | **ต่ำ** (ในโหมด SSO) |
| R11 | เฉลยของชุดทดสอบผิด ทำให้ผลวัดน่าเชื่อถือเกินจริง | ตรวจหลักฐานด้วยโค้ด, เก็บผลรอบ blind แยก, ledger การตรวจเฉลยโดยผู้เชี่ยวชาญ | พบเฉลยผิด/เข้มเกิน 4 จุดและแก้อย่างเปิดเผย | **สูงจนกว่าผู้เชี่ยวชาญยืนยัน** — ตอนนี้ 0 จาก 218 ข้อ |
| R12 | นโยบายภายในที่ใช้เป็นแหล่งตอบไม่ได้รับอนุมัติหรือล้าสมัย | เอกสารต้องมีเจ้าของ ผู้อนุมัติ และวันทบทวน; เฉพาะฉบับ approved ค้นพบ; เตือนเมื่อเกินกำหนด | [governance.md](governance.md) | **ต่ำ** เมื่อใช้นโยบายจริง (ตอนนี้ทั้ง 6 ฉบับเป็นตัวอย่าง) |

## 5. การตรวจสอบความถูกต้อง (Validation)

- ชุดทดสอบ 218 ข้อ ใน 3 ชุด (golden 51, held-out 21, extended 146) ครอบคลุมครบ 14 เอกสาร วัดด้วยเกณฑ์ที่กำหนดผลได้ (ข้อความหลักฐาน, ข้อเท็จจริงที่ต้องมี, การตรวจ quote) ไม่ใช้ LLM เป็นผู้ตัดสิน
- **ตัวเลขที่ควรอ้างสำหรับคำถามที่ไม่เคยเห็น:** รอบแรกแบบ blind — held-out: ค้นพบถูก 94.1%, พฤติกรรมถูก 85.7%; extended: ค้นพบถูก 92.2%, พฤติกรรมถูก 94.5%, ข้อเท็จจริงถูก 91.4%, รั่วไหล 0
  ตัวเลขหลังแก้ไขดีกว่านี้ แต่ไม่ใช่ blind แล้ว (รายละเอียดและรายการข้อผิดพลาด: [evaluation.md](evaluation.md))
- **ข้อจำกัดสำคัญ:** ชุดทดสอบเขียนโดยผู้พัฒนา ยังไม่มีข้อใดที่ผู้เชี่ยวชาญ compliance ยืนยัน ต้องทำก่อนอ้างผลต่อคณะกรรมการ
  (ขั้นตอน: `copilot eval-review export` → ทีม Compliance ตรวจ → `import`; รายงาน `--reviewed-only`)
- การตรวจแบบอิสระ (independent validation) โดยหน่วยงานที่ไม่ได้พัฒนาระบบ: **ยังไม่ได้ทำ** ธนาคารควรกำหนดผู้ตรวจและให้ชุดคำถามของตนเอง
- ผลทดสอบความสามารถรองรับ: ผู้ใช้พร้อมกันบน GPU 8 GB, ~2 คำถาม/วินาทีต่อ process ([deployment.md](deployment.md))

## 6. การติดตามหลังนำไปใช้ และเงื่อนไขการตรวจสอบซ้ำ

มาตรวัดและกฎแจ้งเตือนอยู่ใน `deploy/prometheus/alerts.yml` ตัวชี้วัดที่ควรรายงานต่อคณะกรรมการรายเดือน:
อัตราคำตอบที่ยืนยันอ้างอิงไม่ได้ (เป้า < 5%), อัตรา quote ที่ตรวจผ่าน (> 90%, ปกติ ~96%), อัตราปฏิเสธ (< 40%),
จำนวนรายงานปัญหาแยกประเภทและเวลาปิดเรื่อง, เหตุการณ์ด่วน (ต้องเป็น 0), ผล `audit-verify`, อัตรา 👎, ผลสุ่มตรวจโดยเจ้าหน้าที่

**ต้องตรวจสอบซ้ำ (รัน evaluation ใหม่ และบันทึกผล) เมื่อ:** เปลี่ยนโมเดลหรือผู้ให้บริการ LLM, แก้ prompt, เปลี่ยน embedding/reranker,
เปลี่ยน threshold, เพิ่ม/แก้ glossary, นำเข้าหรือเปลี่ยนเอกสารในคลัง, หรือพบเหตุการณ์ระดับ S1/S2 ([incident-process.md](incident-process.md))

## 7. การควบคุมการเปลี่ยนแปลง

โค้ดทุกการเปลี่ยนแปลงผ่าน pull request และ CI (lint, เทสต์, build); การเปลี่ยนที่กระทบคำตอบต้องแนบผล `copilot eval` (รวม quality gate Hit@6);
เอกสารเข้าคลังผ่าน `copilot add-policy` (ตรวจเจ้าของ/ผู้อนุมัติ/วันทบทวน); ทุกการอนุมัติหรือถอนเอกสารมีบันทึก
(สถานะ `approved`/`draft`/`withdrawn`) ส่วนการ deploy เข้า production ต้องเป็นไปตามกระบวนการของธนาคาร (ไม่ครอบคลุมใน repo นี้)

| DPO | อนุมัติการไหลของข้อมูล ผู้ให้บริการ LLM และอายุการเก็บ |
| ฝ่ายกฎหมาย | รับรองข้อตกลงการใช้งานและข้อความปฏิเสธความรับผิด |
| ความมั่นคงปลอดภัยสารสนเทศ | ทดสอบเจาะระบบ, ตั้งค่า SSO/เครือข่าย/ความลับ ([security.md](security.md)) |
| ตรวจสอบภายใน | ตรวจ audit log และผลการติดตาม |

## 9. เงื่อนไขที่ต้องปิดก่อนใช้งานจริง

ส่วนที่ 5 ของ `evidence/model-card.md` แสดงรายการสดจากระบบ รายการที่ทราบแล้วจากการพัฒนา:

- [ ] แทนที่นโยบายตัวอย่าง 6 ฉบับด้วยนโยบายจริงที่อนุมัติแล้ว และตัดสินว่าต้องเพิ่มกฎหมายฉบับใด
- [ ] ผู้เชี่ยวชาญ compliance ยืนยันเฉลยของชุดทดสอบ แล้วรายงานผลแบบ `--reviewed-only`
- [ ] ผู้ตรวจอิสระทบทวนผลการทดสอบ
- [ ] เลือกผู้ให้บริการ LLM และทำสัญญา (zero-retention, ภูมิภาค); ตัดสินเรื่องการส่งเอกสารชั้นลับ
- [ ] เชื่อม SSO กับ IdP จริง, ปิดบัญชีเดโม, ตั้ง `COPILOT_ENV=production`, `COPILOT_TERMS_REQUIRED=true`, ตั้งโทเค็น metrics
- [ ] ทดสอบเจาะระบบโดยทีมความปลอดภัย
- [ ] ฝ่ายกฎหมายรับรองข้อตกลงการใช้งาน
- [ ] กำหนดผู้รับแจ้งเตือนและผู้รับเรื่องรายงานปัญหา ([incident-process.md](incident-process.md))
- [ ] ฝึกอบรมผู้ใช้กลุ่มนำร่อง ([user-guide.md](user-guide.md)) และกำหนดเกณฑ์ความสำเร็จของการนำร่อง
- [ ] ซ้อมกู้คืนข้อมูลบนสภาพแวดล้อมจริง
