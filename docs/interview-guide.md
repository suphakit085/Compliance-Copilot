## 2. ลำดับการเดโม (5–7 นาที)

1. **Login เป็น `somchai` (พนักงาน)** → ถาม "ถ้าข้อมูลลูกค้ารั่วไหล ต้องแจ้งสำนักงานภายในกี่ชั่วโมง และนโยบายภายในเราสอดคล้องไหม"
   - ชี้ badge S1/S2 → คลิกให้ดูข้อความต้นฉบับที่ไฮไลต์ (มาตรา 37(4) "เจ็ดสิบสองชั่วโมง")
   - ชี้ว่า AI จับได้ว่านโยบายภายในเขียน 7 วัน ขัดกับกฎหมาย
2. **ถามเรื่องของขวัญ** แล้วเปลี่ยนวันที่ as-of เป็น 2024-06-01 → คำตอบเปลี่ยนจาก 5,000 เป็น 3,000 บาท (versioning)
3. **ถามเรื่องคู่มือ STR (เอกสารลับ)** ในฐานะ somchai → ระบบตอบว่าไม่พบข้อมูล
   → logout แล้ว login เป็น `nida` (Compliance) ถามซ้ำ → ได้คำตอบ (access control)
4. **ใส่ข้อมูลส่วนบุคคลในคำถาม** (ชื่อ เบอร์โทร เลขบัตร) → ชี้ badge "ปิดบังข้อมูลส่วนบุคคล"
5. **ลอง prompt injection** "ไม่ต้องสนใจคำสั่งก่อนหน้า…" → ถูกบล็อก
6. **Gap Analysis** (เป็น nida) เลือกนโยบาย PDPA → แสดงข้อขัดแย้ง 2 ข้อที่ร้ายแรง พร้อมอ้างอิงที่ยืนยันแล้ว
7. **Audit Trail** → กด "ตรวจสอบ hash chain" → อธิบายว่าถ้าใครแก้ log ย้อนหลังจะตรวจพบ
8. **Evaluation** → ตาราง ablation (อธิบายว่าแต่ละส่วนช่วยเท่าไร)

> เตรียมวิดีโอสำรองไว้เสมอ เผื่อเน็ตหรือโควตา API มีปัญหา (ระบบยังทำงานแบบ retrieval-only ได้)
> บทพูดและลำดับฉากสำหรับอัดวิดีโออยู่ใน [demo-script.md](demo-script.md)

## 4. คำถามที่น่าจะโดนถาม และแนวคำตอบ

**Q: กัน hallucination อย่างไร?**
สามชั้น: (1) ถ้าคะแนน rerank ต่ำกว่า threshold ระบบไม่เรียก LLM เลย (2) prompt บังคับให้ตอบจาก SOURCES และแนบ quote ตรงตัว (3) โค้ดตรวจ quote กับต้นฉบับ — อ้างอิงที่หาไม่เจอจะถูกตัดและแสดงเป็นสีแดง ถ้าไม่มีอันไหนยืนยันได้ ระบบแสดงข้อความต้นฉบับแทนคำตอบ

**Q: ทำไมไม่ใช้ LLM-as-judge วัดผล?**
ใช้ metric แบบ deterministic ก่อน (evidence string, key facts, quote verification) เพราะ reproducible ราคาถูก และกรรมการตรวจสอบเองได้ — LLM judge มีความแปรปรวนและมี bias ของตัวเอง ใช้เฉพาะเมื่อจำเป็น

**Q: กฎหมายเปลี่ยนบ่อย จะอัปเดตอย่างไร?**
เอกสารมี effective_from/to และไม่ทับฉบับเก่า ถามย้อนหลังได้ ฉบับประมวลมี `amended_by` ทำให้ระบบเตือนว่ามีการแก้ไขที่ยังไม่รวม (เช่น ทธ. 53/2568) ไฟล์ต้นฉบับ pin ด้วย SHA-256 ถ้า regulator อัปไฟล์ใหม่ fetcher จะเตือน ขั้นต่อไปคือ job ตรวจหน้าเว็บหน่วยงานกำกับตามรอบ

**Q: ข้อมูลลับหลุดไปที่ LLM ภายนอกได้ไหม?**
ACL อยู่ใน SQL ของขั้น retrieval เอกสารที่ไม่มีสิทธิ์จึงไม่เข้า prompt ตั้งแต่ต้น PII ถูกปิดบังก่อนเรียก LLM embedding/rerank รันในเครื่อง สำหรับ production ในธนาคาร ระบบออกแบบ provider แบบเสียบเปลี่ยนได้ — ใช้ LLM on-prem หรือ cloud ที่มี data residency และ zero-retention ได้โดยไม่ต้องแก้ส่วนอื่น

**Q: ทำไมใช้ pgvector ไม่ใช้ vector DB เฉพาะทาง?**
ข้อมูลระดับหลักพัน–หลักแสน chunk Postgres พอ และได้ filter สิทธิ์/วันที่ใน query เดียวกับ vector search, transaction เดียวกับ audit log, ทีม DBA ธนาคารดูแลเป็นอยู่แล้ว ถ้าขยายใหญ่มากค่อยพิจารณา OpenSearch/Qdrant

**Q: ภาษาไทยมีปัญหาอะไรพิเศษ?**
(1) ไม่มีช่องว่างระหว่างคำ → ตัดคำด้วย PyThaiNLP ก่อนทำ BM25 (2) PDF ราชการไทยเพี้ยน — "ก าหนด", ฟอนต์ตัวหนาสลับ า/ำ, อักขระ PUA — ต้องซ่อมก่อน index ไม่งั้น search พัง (3) เลขไทย ๒๖ ต้อง normalize (4) หน้าสแกนใช้ OCR และติดป้ายให้ผู้ใช้ตรวจ

**Q: ถ้า retrieval หาไม่เจอแต่ LLM "รู้" คำตอบจาก pretraining จะให้ตอบไหม?**
ไม่ — งาน compliance ต้องอ้างได้ คำตอบที่ไม่มีหลักฐานในคลังเอกสารถือว่าใช้ไม่ได้ ระบบจะบอกว่าไม่พบและแนะนำให้ติดต่อทีม Compliance

**Q: Cost?**
retrieval ฟรี (โมเดล local) LLM ใช้ ~2,000 input + ~500 output token ต่อคำถาม Flash model ราคาต่ำมาก คำถามนอกคลัง/ถูกบล็อกไม่เรียก LLM เลย งาน batch มี cache

**Q: ข้อจำกัดของระบบ?** (ตอบตรง ๆ จะได้คะแนน)
ชุดคำถาม 218 ข้อ (golden 51 + held-out 21 + extended 146) เขียนโดยผู้พัฒนาทั้งหมด ยังไม่มีผู้เชี่ยวชาญยืนยัน ต้องขยายจาก query จริงและให้ทีม compliance review / ตัวเลข held-out หลังแก้ไม่ใช่ blind แล้ว ตัวเลขที่ควรอ้างสำหรับคำถามที่ไม่เคยเห็นคือรอบแรก (พฤติกรรมถูก 85.7%) และต้องเขียนชุด blind ใหม่ทุกครั้งที่แก้ / SSO ทดสอบกับ Keycloak ยังไม่ได้ลองกับ IdP จริงของธนาคาร (single logout, token refresh) / RLS ครอบเฉพาะตารางเอกสาร ส่วนประวัติแชตยังคุมที่ชั้น API / นโยบายภายในเป็นข้อมูลจำลอง

**Q: จะเอานโยบายจริงของธนาคารเข้าระบบอย่างไร และใครรับผิดชอบความถูกต้อง?**
ไฟล์นโยบายต้องมี owner, ผู้อนุมัติ, วันที่อนุมัติ และวันที่ต้องทบทวน ไม่ครบระบบไม่ยอมนำเข้า (`copilot add-policy` ตรวจและแสดงตัวอย่างก่อนว่าระบบอ่านได้กี่ข้อ) เฉพาะสถานะ approved เท่านั้นที่ค้นเจอ ฉบับร่างไม่เข้าดัชนี ฉบับที่ถอนจะถูกลบออกจากดัชนี ฉบับเก่าที่ถูกแทนที่ยังค้นย้อนหลังได้ด้วย effective_to หน้าเอกสารแสดงเจ้าของ/ผู้อนุมัติ/กำหนดทบทวน และเตือนเมื่อเกินกำหนด เรื่องที่ระบบตัดสินแทนไม่ได้ (ใครเป็นเจ้าของ, LLM ผู้ให้บริการรายไหน, retention) รวมไว้เป็น checklist ใน docs/governance.md

**Q: กฎหมายเปลี่ยนแล้วรู้ได้อย่างไร?**
ไฟล์ทุกฉบับตรึงด้วย SHA-256 คำสั่ง `copilot check-updates` ดึงต้นฉบับมาเทียบ ถ้าเปลี่ยนจะคืน exit code 1 (ตั้ง cron/CI ได้) และไม่เขียนทับของเดิม ต้องให้คนอ่านฉบับใหม่ก่อน ข้อจำกัดคือจับได้เฉพาะฉบับที่อยู่ในรายการ กฎหมายฉบับใหม่ต้องมีคนเฝ้าและเพิ่มเข้า sources.yaml ถ้าต้นทางบล็อก ระบบรายงานว่า unreachable ไม่ใช่ unchanged เคสจริงที่เจอ: เว็บ ocs.go.th ไม่ส่ง intermediate certificate ทำให้ Linux/CI ตรวจ TLS ไม่ผ่าน ผมแก้โดยแนบ intermediate ของ GlobalSign ที่ตรวจแล้วว่าต่อถึง root ที่เชื่อถือ แทนการปิดการตรวจ TLS

**Q: ทำ streaming ได้อย่างไรโดยที่ยังตรวจการอ้างอิงก่อนแสดง?**
ตรวจ quote ได้ต่อเมื่อโมเดลเขียนจบ จึงแบ่งเป็นสองระดับ: ระหว่างเขียน ระบบส่งความคืบหน้าจริงของแต่ละขั้น ส่งแหล่งอ้างอิงที่ค้นเจอทันที (ราว 1 วินาที) และส่งข้อความร่างทีละส่วน โดยป้ายกำกับชัดเจนว่า "ร่างคำตอบ ยังไม่ได้ตรวจสอบการอ้างอิง" พอเขียนจบจึงตรวจ quote ทุกตัวกับต้นฉบับ แล้วแทนที่ร่างด้วยคำตอบที่ตรวจแล้ว ถ้าตรวจไม่ผ่านจะแสดงข้อความต้นฉบับแทนร่าง ผลคือผู้ใช้เห็นข้อความแรกใน 2-4 วินาที แทนที่จะรอ 5-30 วินาทีบนหน้าว่าง กรณีขอบ: Gemini ตัด stream กลางทางด้วย 503 บ่อยพอสมควร (เจอจริงตอนทดสอบ) ระบบเริ่มสร้างใหม่และสั่ง UI ทิ้งร่างเดิม ถ้าผู้ใช้ปิดหน้าหลังเห็นร่างแล้ว จะมี audit `chat_interrupted` เก็บข้อความที่ส่งไปแล้ว เพื่อไม่ให้มีข้อความที่ผู้ใช้เห็นโดยไม่มีบันทึก

**Q: พร้อม deploy แค่ไหน และต้องใช้ทรัพยากรเท่าไร?**
มี Docker image ทั้ง API และเว็บ (รันด้วย user ที่ไม่ใช่ root, filesystem อ่านอย่างเดียว, ความลับเป็นไฟล์) และ compose แบบ production ที่เปิดพอร์ตเฉพาะเว็บ API กับฐานข้อมูลอยู่ในเครือข่ายภายใน ผมรัน stack นี้จริงแล้ว ระบบไม่ยอมเริ่มเพราะยังมีบัญชีเดโมที่ใช้รหัสสาธารณะอยู่ ซึ่งเป็นสิ่งที่ตั้งใจไว้ ส่วนเรื่องทรัพยากร ผมวัดจริงด้วย `copilot bench`: บน GPU 8 GB หนึ่ง process ค้นคืนได้ราว 2 คำถามต่อวินาที (ผู้ใช้คนเดียว 0.5 วินาที) เพราะโมเดลมีชุดเดียวหลัง lock ถ้าผู้ใช้พร้อมกัน 8 คนจะรอ 3.5 วินาที ส่วนแบบ CPU อย่างเดียวช้ากว่าราว 20 เท่า จึงใช้ได้แค่เดโม ขยายระบบโดยเพิ่ม replica หนึ่งตัวต่อ GPU และย้าย rate limit ไปที่ gateway

**Q: รู้ได้อย่างไรว่าระบบยังน่าเชื่อถืออยู่หลัง deploy?**
นอกจาก uptime/latency แล้ว metrics วัดสิ่งที่สำคัญกับงาน compliance: สัดส่วนคำตอบที่ยืนยันอ้างอิงไม่ได้ อัตรา quote ที่ตรงกับต้นฉบับ (ปกติ ~97% ต่ำกว่า 90% แจ้งเตือน) อัตราปฏิเสธตอบ และ LLM ที่ล้มจนต้องแสดงแต่ข้อความต้นฉบับ ระบบตรวจ hash chain ของ audit log ทุกชั่วโมง ถ้าถูกแก้ไขจะแจ้งเตือนทันที ใน CI มี quality gate ด้าน retrieval (Hit@6 ≥ 0.95) ที่ไม่ต้องใช้ LLM และการสำรองข้อมูลพิสูจน์ด้วยการกู้คืนจริง ไม่ใช่แค่ dump ออกมา

**Q: กัน brute force และการใช้โควตา LLM เปลืองอย่างไร?**
ใส่รหัสผิด 5 ครั้งบัญชีถูกล็อก 15 นาที (เก็บใน DB อยู่รอดแม้รีสตาร์ต) ชื่อผู้ใช้ที่ไม่มีอยู่จริงถูกนับเท่ากันและเสียเวลาตรวจรหัสเท่ากัน ผู้โจมตีจึงแยกไม่ออกว่าบัญชีมีจริงหรือไม่ มี rate limit ต่อที่อยู่ไคลเอนต์ที่หน้าล็อกอิน และต่อผู้ใช้ที่ /chat (20/นาที) กับ Gap Analysis (5/10 นาที) เพราะทุกคำตอบคือการเรียก LLM ที่เสียเงิน เหตุการณ์ล็อกบัญชีและ rate limit ถูกบันทึกใน audit chain (บันทึกเฉพาะครั้งแรกต่อช่วง เพื่อไม่ให้ผู้โจมตีทำให้ audit บวม) ข้อจำกัดที่ต้องบอกตรง ๆ: ตัวจำกัดอยู่ในหน่วยความจำของแต่ละ instance ถ้ามีหลาย replica ต้องบังคับที่ gateway หรือย้ายไป Redis

**Q: ทำไมไม่เปิด CORS?**
เพราะเบราว์เซอร์คุยกับเว็บ origin เดียว และเว็บส่งต่อไป API ผ่านพร็อกซีที่จำกัดเฉพาะเส้นทางที่อนุญาต API จึงไม่ต้องเปิดให้เว็บอื่นเรียกโดยตรง การไม่ตั้ง CORS คือการตั้งค่าที่ปลอดภัยที่สุด และ CSP กำหนดให้หน้าเว็บเชื่อมต่อได้เฉพาะ origin ตัวเอง

**Q: ระบบเชื่อมกับ SSO ของธนาคารได้ไหม และสิทธิ์มาจากไหน?**
ได้ ใช้ OpenID Connect แบบ authorization code + PKCE ใช้ได้กับ Keycloak / Entra ID / Okta ระบบตรวจลายเซ็น issuer audience วันหมดอายุและ nonce ของ ID token ทุกครั้ง สิทธิ์ (role, แผนก, ชั้นความลับ) มาจาก group ที่ IdP ส่งมา แล้ว map ผ่านไฟล์ config/sso.yaml คนที่ไม่อยู่ใน group ที่ map ไว้จะเข้าไม่ได้ ถอนสิทธิ์ที่ IAM ของธนาคารแล้วมีผลตอนล็อกอินครั้งถัดไป ผู้ใช้ถูกผูกด้วย `sub` ไม่ใช่ username จึงไม่มีทางสวมบัญชีเดิมได้ และบัญชี SSO ใช้รหัสผ่านในระบบไม่ได้

**Q: ถ้านักพัฒนาเขียน SQL ลืมกรองสิทธิ์ เอกสารลับจะรั่วไหม?**
ไม่ เพราะมี Row-Level Security ของ Postgres เป็นชั้นที่สอง การอ่านเอกสารในนามผู้ใช้ทำภายใต้ role `copilot_reader` (อ่านอย่างเดียว) ที่เห็นเฉพาะแถวที่ผู้ใช้มีสิทธิ์ ถ้าไม่ได้ตั้งค่าผู้ใช้จะไม่เห็นอะไรเลย (fail closed) มีเทสต์ที่ลบเงื่อนไขสิทธิ์ออกจาก SQL แล้วยืนยันว่าเอกสารลับไม่รั่ว

**Q: จะให้พนักงานใช้อย่างถูกต้องและรับผิดชอบได้อย่างไร?**
สามชั้น: (1) ข้อตกลงการใช้งานที่ต้องยอมรับก่อนถามได้ — มีเวอร์ชัน บันทึกใน audit และ **บังคับที่ฝั่งเซิร์ฟเวอร์** (ไม่ใช่แค่หน้าจอ) ถ้าแก้ข้อความ ทุกคนต้องยอมรับใหม่ เนื้อหาหลักคือ "ข้อมูลประกอบการตัดสินใจ ไม่ใช่ความเห็นทางกฎหมาย ต้องเปิดต้นฉบับ" (2) การออกแบบ UI: ป้ายสถานะ ป้ายสีแดงเมื่ออ้างอิงตรวจไม่ผ่าน ข้อความ "ร่างคำตอบ" ระหว่างสตรีม (3) คู่มือ + แผนอบรม 80 นาที + แบบทดสอบ 5 ข้อ + แผนนำร่อง 4–6 สัปดาห์พร้อมเกณฑ์ผ่าน (เหตุการณ์ด่วน = 0 ฯลฯ ซึ่งเป็นข้อเสนอเริ่มต้นให้ธนาคารปรับ)

**Q: ถ้าคำตอบผิดแล้วมีคนนำไปใช้ ใครรับผิดชอบและแก้อย่างไร?**
ผู้ใช้กด 👎 เลือกประเภท เรื่องเข้าหน้า "รายงานปัญหา" ของ Compliance (ประเภท "เห็นข้อมูลที่ไม่ควรเห็น" สร้างเหตุการณ์ด่วนใน audit ทันที) มีระดับความรุนแรง S1–S4 พร้อมกรอบเวลาที่เสนอ ผู้รับเรื่องแก้ที่ต้นเหตุ (เอกสาร คำศัพท์ prompt หรือการตั้งค่า) บันทึกสิ่งที่ทำ **ผู้รายงานเห็นผลนั้นในแอป** และเรื่องที่เป็นข้อผิดพลาดจริงถูกแปลงเป็นคำถามทดสอบเพื่อกันซ้ำ (ให้ผู้เชี่ยวชาญเติมเฉลย ไม่ใช้คำตอบของระบบเป็นเฉลย) ผมทดสอบวงจรนี้จริงผ่านหน้าเว็บตั้งแต่รายงานจนผู้รายงานเห็นผล สิ่งที่ธนาคารต้องกำหนดเอง: ชื่อผู้รับเรื่องเวร ช่องทางนอกระบบ และเกณฑ์แจ้งหน่วยงานกำกับ

**Q: เอกสารสำหรับฝ่ายความเสี่ยงโมเดลมีอะไรบ้าง?**
docs/model-risk.md: ขอบเขตและข้อห้ามใช้, การไหลของข้อมูล, ทะเบียนความเสี่ยง 12 ข้อพร้อมมาตรการ หลักฐาน และความเสี่ยงคงเหลือ, การตรวจสอบความถูกต้อง, เงื่อนไขที่ต้องตรวจซ้ำ, ช่องลงนาม และ checklist เงื่อนไขก่อนใช้จริง ส่วนข้อเท็จจริงของระบบ (เวอร์ชัน คลังเอกสาร ผลทดสอบ และการตรวจมาตรการควบคุมสด ๆ) สร้างด้วย `copilot evidence-pack` จากระบบที่รันอยู่ เพื่อไม่ให้เอกสารอนุมัติกับระบบจริงไม่ตรงกัน และมันรายงานข้อค้นพบของตัวเองด้วย (เครื่องพัฒนานี้มี 6 ข้อ เช่น ยังเป็นนโยบายตัวอย่าง ผู้ตรวจเฉลยยังเป็น 0)

**Q: ชุดทดสอบมีกี่ข้อ ใครเป็นคนตรวจเฉลย?**
218 ข้อใน 3 ชุด: golden 51 (ใช้จูนระบบ ตัวเลขจึงมองโลกในแง่ดี), held-out 21 (รันครั้งเดียวแบบ blind) และ extended 146 ที่เขียนหลังจูนเสร็จ ครอบคลุมครบ 14 เอกสาร ผลรอบแรกที่ blind: Hit@6 92.2% (baseline 51.6%), พฤติกรรมถูก 94.5%, ข้อเท็จจริงถูก 91.4%, รั่วไหล 0 ผมซื่อตรงว่า**ยังไม่มีข้อไหนที่ผู้เชี่ยวชาญ compliance ยืนยันเฉลย** (0 จาก 218) เขียนโดยผู้พัฒนาจากตัวบทกฎหมาย จึงทำเครื่องมือให้ทีมตรวจ: ส่งออกเป็น Excel ให้กด ok/fix/reject นำเข้ากลับเข้า ledger ถ้ามีใครแก้คำถามหลังตรวจ การรับรองหมดอายุเอง และรายงานทุกฉบับบอกสัดส่วนที่ผู้เชี่ยวชาญตรวจแล้ว ข้อที่เจอระหว่างทาง: เฉลยของผมเองผิด/เข้มเกินไป 4 ข้อ (ตัวตรวจโค้ดจับได้ 4 ข้อที่ข้อความหลักฐานถูกตัดด้วยตัวแบ่งบรรทัดของ PDF) ซึ่งเป็นเหตุผลที่ต้องมีผู้เชี่ยวชาญ

**Q: ข้อผิดพลาดของระบบมีลักษณะอย่างไร?**
8 ข้อจาก 146: 4 ข้อโมเดลอ้าง quote ที่ไม่ตรงต้นฉบับ ระบบจึงถอยไปแสดงข้อความต้นฉบับแทนคำตอบ (ปลอดภัย แต่ไม่เป็นประโยชน์), 2 ข้อปฏิเสธทั้งที่ตอบได้, และ 2 ข้อสิทธิ์เข้าถึงที่ระบบตอบ "ข้อมูลส่วนนี้ไม่มีให้คุณ" แล้วตอบจากเอกสารที่คุณมีสิทธิ์แทน (ไม่รั่ว แต่เกณฑ์เข้มคาดว่าควรปฏิเสธล้วน ๆ) ที่เจอเป็นรูปแบบ: ช่องว่างคำศัพท์ระหว่างภาษาพูดกับภาษากฎหมาย ("ขนม" vs "ของขวัญ") แก้ด้วย glossary 6 คำ ทำให้ Hit@6 เป็น 97.7% แต่ผมแจ้งว่าตัวเลขนี้ไม่ blind แล้ว และมีการทดลองที่ไม่นำมาใช้ (rerank ด้วยคำถามเดิม ช่วยชุดใหม่แต่ทำ held-out ตก)

**Q: รู้ได้อย่างไรว่าไม่ได้ overfit กับ golden set?**
หลังจูนกับ golden set แล้ว ผมเขียนคำถามใหม่ 21 ข้อแบบที่พนักงานถามจริง (ภาษาพูด เล่าสถานการณ์) แล้วรันครั้งเดียวโดยไม่แก้โค้ด ผลตกลงจริง — พฤติกรรมถูก 85.7% ข้อเท็จจริงถูก 76.5% — แปลว่า 100% ใน golden set มองโลกในแง่ดีเกินไป และเจอบั๊กสามจุด: (1) ถามว่านโยบาย 45 วันถูกกฎหมายไหม ระบบตอบจากนโยบายโดยไม่ดึงมาตรา 30 (30 วัน) มา (2) threshold 0.15 สูงเกิน คำถาม "กระเช้าปีใหม่" ได้คะแนน 0.04 จึงถูกปฏิเสธทั้งที่คำตอบมีในคลัง (3) "คุณสมศรี มีสุข" ไม่ถูกปิดบัง แก้ครบพร้อม regression test ผมเก็บผลรอบ blind ไว้ใน repo และรายงานแยกกับรอบหลังแก้อย่างตรงไปตรงมา

**Q: เล่าตัวอย่างที่ eval ช่วยให้เจอปัญหา**
คำถาม "ข้อมูลส่วนบุคคลอ่อนไหวมีอะไรบ้าง" ระบบตอบว่าไม่พบหลักฐาน (ดีที่ไม่มั่ว) แต่ที่จริงคำตอบอยู่ในมาตรา 26 — สาเหตุคือกฎหมายไม่ใช้คำว่า "อ่อนไหว" เลย เป็น vocabulary gap จึงเพิ่ม domain glossary ที่ map ภาษาที่คนถามกับถ้อยคำในกฎหมาย ผลคือ Hit@6 เป็น 100% และแก้กรณี Gap Analysis ที่พลาดเรื่องข้อมูลชีวภาพไปพร้อมกัน

**Q: จะวัดผลหลัง deploy อย่างไร?**
feedback 👍👎 ผูกกับ audit id, ติดตาม abstention rate, สัดส่วน citation ที่ยืนยันไม่ได้, latency p95, และสุ่ม review คำตอบโดยเจ้าหน้าที่ compliance ทุกสัปดาห์ เพิ่มเคสที่ผิดเข้า golden set (regression)

## 5. สิ่งที่ควรเน้นว่า "คิดแบบ compliance"

- AI ช่วย *ค้นและอ้างอิง* ไม่ได้ *ตัดสินแทน* — Gap Analysis ออกมาเป็น worklist ให้คนทบทวน
- ทุกการตัดสินใจของระบบ trace ย้อนกลับได้ (audit + prompt version + model version)
- เมื่อไม่แน่ใจ ระบบเลือก "ไม่ตอบ" มากกว่า "ตอบผิด"

**Q: เล่าตัวอย่างที่การวัดผลช่วยจับบั๊กได้ (อีกตัวอย่าง)**
รอบแรกได้ 96% และพบ 2 ข้อที่พลาด ข้อแรก ตัวกรอง prompt injection บล็อกคำถาม "กฎกระทรวงยกเลิกกฎกระทรวงฉบับใด" เพราะคำว่า "ยกเลิก…กฎ" ซึ่งเป็นภาษากฎหมายปกติ แก้ให้จับเฉพาะเมื่ออ้างถึงคำสั่งของระบบ ข้อสอง คำถาม "นโยบายเราสอดคล้องกับกฎหมายไหม" ค้นเจอแต่นโยบาย เพราะคำถามเอ่ยชื่อนโยบาย จึงเพิ่มขั้นค้นกฎหมายที่กำกับข้อนโยบายนั้นอีกรอบ ทั้งสองข้อมี regression test และผลรอบใหม่ได้ 100%
