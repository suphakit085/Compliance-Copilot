# กระบวนการเมื่อคำตอบผิด หรือระบบทำงานผิดปกติ

ระบบไม่มีทางถูกทุกครั้ง สิ่งที่ทำให้ใช้ได้อย่างมีความรับผิดชอบคือมีเส้นทางที่ชัดเจนว่า **ใครรับเรื่อง ใครแก้ ใครบอกผู้ใช้
และเรื่องนั้นกลับมาป้องกันซ้ำได้อย่างไร** เอกสารนี้กำหนดเส้นทางนั้น และบอกว่าระบบช่วยตรงไหน
ระดับความรุนแรงและกรอบเวลาเป็น **ข้อเสนอเริ่มต้น** ธนาคารต้องปรับให้ตรงกับนโยบายบริหารเหตุการณ์ของตนและกำหนดผู้รับผิดชอบเป็นรายชื่อจริง

## 1. ระดับความรุนแรง

| ระดับ | ตัวอย่าง | เป้าหมายตอบรับ | เป้าหมายแก้/ควบคุม |
|---|---|---|---|
| **S1 วิกฤต** | ผู้ใช้เห็นเอกสารหรือข้อมูลเกินสิทธิ์; audit chain ไม่ผ่านการตรวจ; ข้อมูลส่วนบุคคลถูกเก็บในที่ที่ไม่ควร | ภายใน 1 ชั่วโมง | ควบคุมความเสียหายภายในวันเดียวกัน (ระงับเอกสาร/ปิดการใช้ชั่วคราว) |
| **S2 สูง** | คำตอบผิดในเรื่องที่นำไปสู่การรายงานหน่วยงานกำกับ ตัวเลขกำหนดเวลา/โทษ/ขั้นต่ำผิด และมีผู้นำไปใช้แล้ว; ระบบใช้กฎหมายฉบับที่ถูกยกเลิก | ภายใน 1 วันทำการ | ภายใน 3 วันทำการ |
| **S3 กลาง** | คำตอบไม่ครบ/อ้างอิงไม่ตรง/ปฏิเสธทั้งที่มีข้อมูล ไม่ถูกนำไปใช้ | ภายใน 2 วันทำการ | ภายในรอบปรับปรุง (ไม่เกิน 2 สัปดาห์) |
| **S4 ต่ำ** | เรื่องการใช้งาน ถ้อยคำ ความช้า | ภายใน 5 วันทำการ | ตามคิวงาน |

การจัดระดับเริ่มจากประเภทที่ผู้ใช้เลือก (`เห็นข้อมูลที่ไม่ควรเห็น` = S1 โดยอัตโนมัติ) แล้วเจ้าหน้าที่ Compliance ปรับตามผลกระทบจริง

## 2. บทบาท

| บทบาท | หน้าที่ | ในระบบ |
|---|---|---|
| ผู้รายงาน (ผู้ใช้ใดก็ได้) | กด 👎 เลือกประเภท เขียนสั้น ๆ | ปุ่มใต้คำตอบ |
| **ผู้รับเรื่อง** (เจ้าหน้าที่ Compliance ที่ธนาคารกำหนดเป็นเวร) | ดูรายงานใหม่ จัดระดับ มอบหมาย | หน้า "รายงานปัญหา" (เมนูของ Compliance/ผู้ตรวจสอบ/ผู้ดูแลระบบ), `copilot feedback-report --open` |
| **เจ้าของการแก้ไข** | แก้ที่ต้นเหตุตามหัวข้อ 4 | แล้วแต่ต้นเหตุ |
| ผู้ปิดเรื่อง (Compliance / ผู้ดูแลระบบ) | บันทึกสิ่งที่แก้หรือเหตุผลที่ไม่แก้ → **ผู้รายงานเห็นข้อความนี้** | ปุ่ม "แก้ไขแล้ว"/"ปิดเรื่อง", `copilot feedback-resolve` |
| ผู้ตรวจสอบภายใน | ดูแนวโน้ม ตรวจว่าเรื่องถูกปิดครบ | หน้า Audit Trail และรายงานปัญหา (อ่านอย่างเดียว) |
| เจ้าของระบบ | ตัดสินกรณี S1/S2 และการแจ้งผู้เกี่ยวข้อง | — |

## 3. ขั้นตอน

1. **รับ** — รายงานเข้าสถานะ `open` และมีหมายเลขเรื่อง ผูกกับเลข audit ของคำตอบ (เห็นคำถามที่ปิดบัง PII แล้ว, เอกสารที่ถูกดึงมา, สถานะคำตอบ,
   อัตราอ้างอิงที่ยืนยันได้) รายงานประเภท leak สร้างเหตุการณ์ `incident_reported` ในบันทึกตรวจสอบทันที
2. **จัดระดับและมอบหมาย** ตามหัวข้อ 1
3. **ควบคุมความเสียหาย (S1/S2)** — ก่อนหาสาเหตุ: ระงับเอกสารที่เกี่ยวข้อง (เปลี่ยนสถานะเป็น `withdrawn` แล้ว `copilot ingest` ซึ่งถอนออกจากดัชนีทันที),
   หรือปิดการใช้งานชั่วคราว; S1 ให้ตรวจ `GET /audit/verify` และดูบันทึกการเข้าถึงว่าใครเห็นอะไร
4. **หาต้นเหตุ** — เปิดบันทึกของคำตอบนั้นด้วยเลข audit (หน้า Audit Trail) ดูว่าเอกสารไหนถูกดึงมา คะแนนเท่าไร และ quote ตรวจผ่านหรือไม่ (หัวข้อ 4)
5. **แก้ที่ต้นเหตุ** และ **รัน evaluation ใหม่** (หัวข้อ 5)
6. **ปิดเรื่อง** พร้อมบันทึกที่ผู้รายงานอ่านเข้าใจได้ เช่น "เพิ่มฉบับ ... เข้าคลังแล้ว" หรือ "ตรวจแล้ว คำตอบถูกต้อง เหตุที่ดูต่างคือ ..."
7. **แจ้งผู้ใช้ที่อาจได้รับผลกระทบ (S1/S2)** — ผู้รับเรื่องตรวจจากบันทึกตรวจสอบ (หน้า Audit Trail) ว่าใครถามเรื่องเดียวกันในช่วงที่ปัญหาอยู่ เจ้าของระบบตัดสินว่าจะแจ้งใคร
   และต้องแจ้ง DPO หากเกี่ยวข้องกับข้อมูลส่วนบุคคล (พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล: ประกาศ กคส. เรื่องการแจ้งเหตุละเมิด อยู่ในคลังเอกสารของระบบเอง)
8. **ทบทวนหลังเหตุ (S1/S2)** — ภายใน 5 วันทำการ ใช้แบบฟอร์มหัวข้อ 6

## 4. ต้นเหตุ → วิธีแก้

| อาการ | มักเกิดจาก | แก้ที่ | ตรวจด้วย |
|---|---|---|---|
| ตอบตามฉบับเก่า / ไม่ใช้ฉบับแก้ไข | ไม่มีฉบับใหม่ในคลัง หรือวันที่มีผลผิด | เพิ่มเอกสารใน `data/sources.yaml` + `copilot fetch/ingest`, ใส่ `effective_from/to`, `amended_by` | `copilot check-updates`; คำถามเวอร์ชันใน evaluation |
| ระบบปฏิเสธทั้งที่มีข้อมูล | คำศัพท์คนถามต่างจากกฎหมาย | เพิ่มคำใน `data/glossary.yaml` (ต้องระบุ `source`) | evaluation ทั้ง 3 ชุด — ระวังคำใหม่ทำให้คำถามอื่นแย่ลง (เคยเกิดและแก้แล้ว) |
| อ้างอิงไม่ตรง / quote ไม่ผ่าน | โมเดลสรุปเกิน/อ้างผิดที่ | ปรับ prompt หรือเปลี่ยนโมเดล (เปลี่ยนเวอร์ชัน prompt) | evaluation: อัตรา quote ที่ตรวจผ่าน, คำตอบที่ยืนยันไม่ได้ |
| ตอบผิดเพราะเอกสารต้นทางอ่านผิด | PDF ไทยเพี้ยน (สระอำ, ฟอนต์) | แก้ใน `ingestion/thai_text.py`/`pdf_extract.py` + เทสต์ + `copilot ingest --force` | เทสต์ ingestion; ตรวจข้อความที่หน้า "คลังเอกสาร" |
| นโยบายภายในขัดกฎหมาย (แต่ระบบตอบตามนโยบาย) | นโยบายผิดจริง | แก้นโยบาย (เจ้าของนโยบาย) ไม่ใช่ระบบ — Gap Analysis ช่วยชี้ | Gap Analysis |
| เห็นเอกสารเกินสิทธิ์ | ตั้ง `classification`/`departments` ผิด หรือบั๊กในการกรองสิทธิ์ | แก้ front matter ของเอกสาร; ถ้าเป็นบั๊ก แก้โค้ด + เทสต์ที่ลบเงื่อนไขสิทธิ์ | เทสต์สิทธิ์ + RLS; evaluation หมวด rbac |
| คำตอบไม่ผิด แต่ผู้ใช้เข้าใจผิด | การอบรม/ถ้อยคำ | ปิดเรื่องพร้อมคำอธิบาย (`ปิดเรื่อง`) และปรับคู่มือ | — |

## 5. ให้เรื่องหนึ่งกลับมาป้องกันซ้ำ

ทุกเรื่องที่เป็นข้อผิดพลาดจริงควรกลายเป็นคำถามทดสอบ: `copilot feedback-report --draft <เลข audit>` สร้างร่างใน `eval/inbox/`
(มีคำถามที่ปิดบังแล้วและสิ่งที่เกิดขึ้น ส่วนเฉลยเว้นว่างให้ผู้เชี่ยวชาญเติม) → ผู้เชี่ยวชาญเติมพฤติกรรมที่ถูกต้อง หลักฐาน และข้อเท็จจริงที่ต้องมี →
ย้ายเข้าชุดคำถาม ส่งตรวจผ่าน `copilot eval-review` → รัน `copilot eval` ทั้งสามชุด และ `--production-only` เป็นประตูใน CI
(รายละเอียด: [evaluation.md](evaluation.md))

## 6. แบบทบทวนหลังเหตุ (S1/S2)

```
เรื่องที่ #____  ระดับ ____  วันที่พบ ____  วันที่ควบคุมได้ ____  วันที่ปิด ____
1. เกิดอะไรขึ้น (ข้อเท็จจริง ไม่ใช่การกล่าวโทษ)
2. ผู้ใช้/ข้อมูลที่ได้รับผลกระทบ และมีการนำคำตอบไปใช้จริงหรือไม่
3. ต้นเหตุ (หัวข้อ 4) และเหตุที่ระบบ/มาตรการเดิมไม่จับได้
4. สิ่งที่แก้ทันที / สิ่งที่แก้ถาวร / ผู้รับผิดชอบ / กำหนดเสร็จ
5. ข้อสอบ (คำถามทดสอบ) ที่เพิ่ม และผล evaluation ก่อน-หลัง
6. ต้องเปลี่ยนมาตรการควบคุม คู่มือ หรือการอบรมหรือไม่
7. แจ้งผู้ที่เกี่ยวข้องแล้วหรือยัง (ผู้ใช้ / DPO / ผู้บริหาร / หน่วยงานกำกับตามเกณฑ์ของธนาคาร)
```

## 7. สิ่งที่เอกสารนี้ไม่ได้กำหนด

ชื่อผู้รับเรื่องเวร, ช่องทางแจ้งเหตุนอกระบบ (โทรศัพท์/ticket), เกณฑ์การแจ้งหน่วยงานกำกับ และกรอบเวลาตามนโยบายของธนาคาร
— ต้องกำหนดโดยธนาคาร ระบบเก็บหลักฐานและเครื่องมือไว้ให้ แต่ไม่ได้แทนการตัดสินใจเหล่านั้น
